# Unified tests

This directory holds MSIM's "unified" test suite: a single BATS (Bash
Automated Testing System) suite that covers both architecture-specific
guest-code tests (MIPS32, RISC-V32) and architecture-independent tests of
MSIM itself (device errors, CLI behaviour, ...).

Tests are described declaratively as files/directories under `src/tests/`.
A generator script, `discover.py`, walks that tree and produces two
generated files:

- `rebuild.mk` — a Makefile fragment with the build recipes needed to
  assemble/compile/link every test's boot loader and/or kernel image and to
  assemble each test's `msim.conf`.
- `all.bats` — the actual BATS test file, with one `@test` per discovered
  test case.

The build products (`images/<test>/...`) and `all.bats` are committed to
git, so `./all.bats` (or `make run-tests`) can be run right away without a
cross-toolchain installed. `rebuild.mk` and `local.mk` are local/generated
and are gitignored (see `.gitignore`); you only need a toolchain when you
actually run `make rebuild`.

## Directory layout

```
tests/unified/
├── discover.py           # test discovery + generator (see below)
├── Makefile              # entry point: rebuild / run-tests / clean
├── rebuild.mk            # GENERATED by discover.py, not committed
├── all.bats              # GENERATED by discover.py, committed
├── common.bash           # BATS helper functions used by all.bats
├── toolchain.mk           # default toolchain flags/paths (mips32-*, riscv32-*)
├── local.mk.template     # copy to local.mk to override toolchain paths
├── local.mk              # local, gitignored toolchain path overrides
├── src/
│   ├── tests/            # one subtree per test case, see "Test discovery"
│   │   ├── msim.boot.<arch>.conf    # default msim.conf for boot-only tests
│   │   └── msim.kernel.<arch>.conf  # default msim.conf for kernel tests
│   ├── shared/           # boot.S / kernelhead.S / include/ shared by all tests
│   └── *.lds             # linker scripts (boot.<arch>.lds, kernel.<arch>.lds)
└── images/               # GENERATED build output, one dir per test, committed
    └── <test-target>/    # msim.conf, {boot,kernel}.bin, *.expected
```

## Test discovery (`discover.py`)

`discover.py` looks for test directories two levels below `src/tests`,
i.e. every `src/tests/<category>/<case>` directory becomes one candidate
test named `<category>/<case>` (e.g. `src/tests/basic/printer` →
`basic/printer`). For each candidate, the *kind* of test is determined by
which files are present:

1. **System test** — the directory contains `msim.sys.conf`.
   This is a single, architecture-independent test (arch tag `sys`) that
   only exercises MSIM itself (e.g. invalid device configuration); no
   guest code is built.
2. **C kernel test** — the directory (or a file found while walking
   upwards, see below) contains `kernel.c`.
   One test is generated *per architecture* in `ARCH_LIST` (`mips32`,
   `riscv32`). The kernel is linked from the shared
   `src/shared/kernelhead.<arch>.S` plus `kernel.c`, using
   `src/kernel.<arch>.lds`. The boot loader is always the shared
   `src/shared/boot.<arch>.S` / `src/boot.<arch>.lds`.
3. **Arch-specific kernel test** — the directory contains `kernel.<arch>.c`
   or `kernel.<arch>.S` (checked per architecture independently, so a test
   can exist for only one arch — e.g. a test that's inherently RISC-V-only,
   like one exercising Sv32 paging, just ships a `kernel.riscv32.c`, no
   MIPS variant). Same shared boot loader as the C kernel test above;
   `kernel.<arch>.c` (or `kernel.<arch>.S`) is used instead of the
   cross-arch `kernel.c`.
4. **Boot-only test** — the directory contains `boot.<arch>.S` (and no
   kernel at all). Only a boot loader is built, linked with the nearest
   `boot.<arch>.lds` found by walking up from the test directory (falling
   back to `src/boot.<arch>.lds`).

A single `src/tests/<category>/<case>` directory can therefore expand into
several generated test cases: one `sys` test, or one test per matching
architecture.

### `test.ini`

An optional `test.ini` file (single unnamed section, parsed with
`configparser`) lets a test override defaults:

```ini
exit_code = 3
name = some/other-name
```

- `exit_code` — the exit code MSIM is expected to terminate with
  (default `0`). Any non-zero value flips the generated BATS test to
  expect failure (see `msim_run_sys`/`exit_success` below).
- `name` — overrides the test's display/target name (defaults to the
  `<category>/<case>` path).

### Locating `msim.conf`

For non-system tests, `discover_msim_conf()` looks for an `msim.<arch>.conf`
file starting at the test directory and walking upwards, falling back to
`src/tests/msim.<boot|kernel>.<arch>.conf` if none is found closer. In
addition, any of the following *append* files found while walking upwards
are concatenated (in nearest-to-farthest, then this exact order) onto the
base config: `msim.<boot|kernel>.<arch>.conf.append`,
`msim.<arch>.conf.append`, `msim.<boot|kernel>.conf.append`,
`msim.conf.append`. This lets a whole subtree of tests (e.g. everything
under `src/tests/dnomem/`) share extra `msim.conf` lines (such as an added
device) without repeating them, while individual tests can add further
lines of their own.

### Trap/interrupt handlers

A test that needs `mtvec`/`stvec` to point somewhere does **not** need a
separate ROM device for that: since the boot loader/kernel is linked (not
just assembled), a handler can simply be a label in the test's own
source, loaded at whatever address the linker places it, referenced with
`la` when filling in the CSR:

```asm
la t0, my_handler
csrw mtvec, t0
...
my_handler:
    ...
```

RISC-V assembly files get `-Isrc/shared` on their include path (see
`toolchain.mk`), so the common "write a character to the printer and
halt" handler body doesn't need to be retyped in every test that wants a
simple success/failure marker — `src/shared/marker_handler.riscv32.inc`
defines it once as a `.macro`, and a test just does:

```asm
#include "marker_handler.riscv32.inc"
...
success_handler:
    write_marker_and_halt 'S'
failure_handler:
    write_marker_and_halt 'F'
```

This keeps a test's guest code, its handler(s), and its `msim.conf` (just
`boot`/`kernel` plus whatever devices the test is actually about — no
extra handler ROMs) all in one place. See `riscv32/exc-*` or
`riscv32/tlb` for worked examples — `tlb` even reuses its own existing
"the test failed" label as the trap target directly, since a label
doesn't care whether it's reached by a branch or by a trap.

### Extra ROM/data images

Occasionally a test genuinely needs content at another address that
*isn't* just a handler — e.g. `riscv32/virtual-addressing` sets up its
own page tables and needs a separate user-mode program (`app.riscv32.S`)
to map into them, which can't be folded into the main kernel image (the
whole point is that it's reached through a *different* address-space
context). For this, `discover.py` scans the test's own (already resolved)
`msim.conf` for every `... load "<name>.bin"` line, and for each `<name>`
other than `boot`/`kernel` resolves it, in order:

1. `<name>.<arch>.S` in the test's own directory, or
2. `<name>.<arch>.S` in `src/shared/`, or
3. otherwise `<name>.bin` in the test's own directory, copied verbatim (a
   static, non-executable fixture, same treatment as `guest.expected` —
   this is how the `data.bin` memory fixtures used by e.g.
   `riscv32/loads` are picked up).

A `.S` match is built through the same assemble → link → objcopy pipeline
as the boot loader, linked with, in order: a test-local `<name>.<arch>.lds`
if present, otherwise a *shared*, name-matched `src/<name>.<arch>.lds` if
one exists, otherwise `src/boot.<arch>.lds` as a last resort (fine for
small, position-independent snippets, since it's the test's own
`msim.conf` that decides at which physical address the resulting `.bin`
is actually loaded). The shared-linker-script case is how `app.<arch>.S`
gets a stable, framework-wide meaning: `src/app.riscv32.lds` always links
it at the same fixed address, so any test's `kernel.<arch>.c` can map that
one well-known address into its own page tables without needing to know
where the app's *own* code/data happen to live. Either way the built
result ends up as `images/<target>/<name>.bin`, matching the literal
filename the test's `msim.conf` already asked for — see the next section
for how that filename gets resolved to a real path at test time.

There is no `test.ini` declaration for any of this — what a test's
`msim.conf` loads *is* what gets built; nothing to keep in sync.

### Locating expected outputs

For each test, `guest.<arch>.expected` (fallback `guest.expected`) is the
expected output produced by the guest program itself (e.g. via the
printer device), and `host.<arch>.expected` (fallback `host.expected`) is
the expected stdout/stderr of MSIM.

## Generated Makefile (`rebuild.mk`)

For every discovered test, `discover.py` emits a `build_<target>` rule
into `rebuild.mk`, where `<target>` is the test's name with `/` and `-`
replaced by `_`, suffixed with `__<arch>` (e.g.
`basic/printer` on MIPS32 → `basic__printer__mips32`). Each rule builds,
under `images/<target>/`:

- `msim.conf` — concatenation of the resolved base config and any
  `.append` files (for `sys` tests, a trailing `quit` line is appended too).
- `guest.expected`, `host.expected` — copies of the resolved expected-output
  files.
- `boot.o` → `boot.raw` → `boot.bin` — assembled/linked/objcopy'd boot
  loader, when the test has one.
- one `.o` per kernel source (`.S` via `$(<ARCH>_AS)`, `.c` via
  `$(<ARCH>_CC)`) → `kernel.raw` → `kernel.bin`, when the test has a kernel.
- one `<name>.o` → `<name>.raw` → `<name>.bin`, or a verbatim copy, per
  extra ROM/data image referenced from the test's `msim.conf` (see "Extra
  ROM/data images" above).

`rebuild.mk` also includes `toolchain.mk` (default cross-toolchain flags
and binary names, e.g. `MIPS32_AS`, `RISCV32_CC`, ...) and, if present,
`local.mk` (see below). Intermediate/non-deterministic build products
(`*.o`, `*.raw`) are tracked for `make clean`; the final `msim.conf`,
`*.bin` and `*.expected` files are committed to git.

## Generated BATS file (`all.bats`)

For every discovered test, `discover.py` emits one `@test` block that
calls a helper from `common.bash`:

- `msim_run_sys "images/<target>"` for `sys` tests (with
  `exit_success=false` prefixed when `exit_code != 0`).
- `msim_run_code "images/<target>"` for architecture tests — this runs
  MSIM against the test's `boot.bin`/`kernel.bin`, capturing both MSIM's
  own output (compared against `host.expected`) and, when the config uses
  a `printer` device, the guest's redirected printer output (compared
  against `guest.expected`).

`msim_run_code` (in `common.bash`) copies the test's `msim.conf` into a
scratch directory and rewrites every quoted `"<name>.bin"` reference in it
to the absolute path of `images/<target>/<name>.bin` — this is what lets a
test's `msim.conf` refer to `boot.bin`, `kernel.bin`, or any extra
ROM/data image by its plain name, and is also exactly what `discover.py`
scans to find those extra images in the first place (see "Extra ROM/data
images" above).

## Running the tests

```sh
./all.bats            # or: make run-tests
```

This only needs the already-built (committed) contents of `images/`.

## Adding/changing tests and rebuilding

If you add, remove, or modify a test under `src/tests/`, regenerate and
rebuild the images, then re-run the tests:

```sh
make rebuild     # regenerates rebuild.mk + all.bats, then builds images/
make run-tests   # or ./all.bats
```

`make rebuild` requires the cross-toolchains for MIPS32 and RISC-V32.
By default it expects them on `$PATH`; if yours are installed elsewhere,
copy `local.mk.template` to `local.mk` and set `MIPS32_TOOLCHAIN_BIN` /
`RISCV32_TOOLCHAIN_BIN` (e.g. to `/opt/mffd3s/<arch>/bin/` for the
NSWI200/MFF toolchain).

Remember to commit the resulting changes under `images/` and the
regenerated `all.bats` — but not `rebuild.mk` or `local.mk`, which are
local/generated and gitignored.

`make clean` removes the generated build products listed in `rebuild.mk`
(requires having run `make rebuild` at least once, since `rebuild.mk`
itself is not committed).
